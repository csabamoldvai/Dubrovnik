Dubrovnik Workbench – how it works

A short description of how the program talks to the board, what happens at start-up with and without a device, and how it notices that the board went away. Written for people who maintain or extend the program; the code snippets are shortened copies of the real code.

1. The pieces

The PC application is a front end. Everything it does is a text command sent over a USB serial connection to Tiberias, the firmware on the Dubrovnik board. A button such as Erase only builds a command line, sends it and shows the reply.

FileRole
dubGui/dubrovnik_workbench.pyThe Workbench window (CustomTkinter): panels, Terminal, menus, start-up logic. dubrovnik_workbench_classic.py is the same program with the original tkinter look.
dubLibs/boardcom.pyThe serial link: finds the COM port, connects, send() a command and response().
dubLibs/dubrovnik.pyFlash functions built from commands: erase, program, read, Quad Enable, part number.
dubLibs/run_cmd_script.py, run_py_script.pyCommand scripts and Python scripts (the dub object).
dubLibs/cfgfile.py, tools.py, documents.pySettings file, Tools menu, Help → Documents.

One window object per concern: serCom (the Serial Connection panel and the connection state), term (the Terminal) and the Erase, Program and Read panels. serCom.portStatus is either 'connected' or 'disconnected', and everything else asks that.

2. Start-up scenarios

At start the program lists the serial ports made by FTDI (the USB-serial chip of the board), then looks at the Auto connect setting.

# boardcom.py
def getPortList(self):
    ports = serial.tools.list_ports.comports()
    return [p.device for p in ports if p.manufacturer == 'FTDI']
SituationWhat happensStatus bar
A. Board on, device in the socket, Auto connect on Connects to the last used port (or the only port). Sends ver to wake the processor, clears the Terminal, sends config and finds a part number, then reads it for the status bar. Connected: COM5 (...) Device: AT25XE321D
B. Board on, no device, Auto connect on Same, but config reports Part# = unknown. A warning asks you to install a device and press RESET. After you click OK the Terminal is still fully usable: volt, freq and config do not need a device. Connected: COM5 (...) (no device)
C. Board on, Auto connect off Nothing is connected. The port list is filled; choose a port and click Connect (see section 3). empty (nothing connected)
D. Board off or unplugged (no COM port), Auto connect on A warning says that no board was found: connect the cable, switch on, press RESET. The program keeps running; the port list is refreshed when you click Connect. empty (nothing connected)
E. Board off, Auto connect off No message at start. Clicking Connect looks for a port again and, if there is none, shows the same warning. empty; No COM port found: ... once the port list has been refreshed

The start-up code for scenarios A and B:

# dubrovnik_workbench.py, end of start-up
if serCom.autoConnect and portList:
    serCom.connectPort(serCom.lastUsedPort, checkIsFlashPresent=False)
    if serCom.portStatus == 'connected':
        comm.connectToMCU()               # 'ver': the processor may need a RESET to boot
        term.clear()
        if comm.isFlashPresent() == 0:    # 'config' says Part# = unknown
            showwarning('Warning', 'No flash device detected\nInstall a device and RESET the board')
        else:
            serCom.deviceDetected(du.get_part_number(comm))   # show it in the status bar
Why the part number is not read inside connectPort here: at this point the USB-serial chip is connected but the processor behind it may not be running yet. connectToMCU is the first command that needs an answer from it.

3. Connecting by hand

When you click Connect, connectPort opens the port, sets the button to Disconnect and, unless told not to, reads the part number straight away:

# dubrovnik_workbench.py, SerComFrame.connectPort (shortened)
self.portHandle = self.comm.connect(self.selPort)
if self.portHandle is None:                 # could not open: another program has it?
    stsBarComm.configure(text=f'Could not open {self.selPort}')
    return
self.portStatus = 'connected'
self.serParams = f'Connected: {self.comPort} (...)'
if checkIsFlashPresent and self.comm.isFlashPresent():
    self.serParams += '    Device: ' + du.get_part_number(self.comm)
stsBarComm.configure(text=self.serParams)

If the board is on but its processor does not answer, the first command waits two seconds and then a Retry / Cancel dialog asks you to switch the board on or press RESET.

4. While the program runs

How a command goes

boardcom.send() empties the input buffer, writes the command plus a carriage return and then reads until the prompt >>> arrives. The text before the prompt is the reply.

# boardcom.py, BoardComm.send (shortened)
self.handle.reset_input_buffer()
self.handle.write((cmdstr + '\r').encode('utf-8'))
self.raw = self.handle.read_until(expected=self.prompt).decode('utf-8')
while self.raw == "":                      # nothing came back within the timeout
    if not askretrycancel('Communication Error: Serial Port Timeout',
                          'Is the board turned ON?\nPress the RESET button'):
        sys.exit()

The serial timeout is 2 seconds while connecting and is raised to 200 seconds after the processor answers, so a chip erase that takes minutes does not time out.

Text the board sends by itself

Besides replies, the board prints messages on its own, for example after RESET. The Terminal checks for them every 100 ms, but only while no command is in progress, so it never steals the reply of a command:

# dubrovnik_workbench.py, Terminal.pollSerial (shortened)
if handle is not None and handle.is_open and not self.cmdInProgress:
    n = handle.in_waiting                  # raises if the port has vanished
    if n > 0:
        data = handle.read(n).decode('utf-8', errors='replace')
        self.txt.insert(END, data)
        self.watchBootMessage(data)        # keeps the status bar in step (section 5)
self.after(100, self.pollSerial)

Scripts

Command scripts and Python scripts run on the window thread. After every command they call root.update(), so the window stays alive and Esc is noticed. While a script runs the panels and the Terminal command line are blocked (serCom.scriptRunning). Dialogs asked by a script come from dialogBox.

5. The board is switched off and on

Often the USB-serial chip stays powered from USB when only the board's own supply is switched off. The COM port then never disappears, so the program stays connected. When the board comes back it detects its device and prints a banner:

Detecting flash part...
Manufacturer Id: 1f (location 0) - Adesto/Atmel
Part info:       AT25XE321D 32Mbit 1.65V-3.60V

The same banner appears after the RESET button. pollSerial passes every chunk it reads to watchBootMessage, which keeps a small text buffer and looks for two phrases:

# dubrovnik_workbench.py, Terminal.watchBootMessage (shortened)
self.bootBuf = (self.bootBuf + data)[-2000:]
if 'Detecting flash part' in self.bootBuf:
    serCom.deviceDetected('')              # the old device is gone until the board says otherwise
    self.bootBuf = self.bootBuf.split('Detecting flash part')[-1]
m = re.search(r'Part info:\s*(\S+)\s', self.bootBuf)   # the whole word has arrived
if m:
    serCom.deviceDetected(m.group(1))
    self.bootBuf = ''
EventResult
Board off, then on, device in the socketThe device disappears from the status bar, then returns with its part number.
Board on, device removed, then RESETThe banner has no Part info line: the status bar shows no device.
Device inserted, then RESETThe banner has Part info: the status bar shows it.
Device inserted or removed without a RESETNot noticed. The board only detects its device at power-up or RESET.

6. The connection is lost

If the USB cable is unplugged, or the USB-serial chip loses power, the COM port disappears. Two checks notice it:

CheckHow
Terminal.pollSerial, every 100 mshandle.in_waiting raises an exception when the port is gone.
SerComFrame.checkLink, every 2 sCompares the connected port with the list of ports Windows reports. A backup for the first check.
# dubrovnik_workbench.py, SerComFrame (shortened)
def checkLink(self):
    if self.portStatus == 'connected':
        if self.selPort not in self.comm.getPortList():
            self.connectionLost()
    self.after(2000, self.checkLink)

def connectionLost(self):
    if self.portStatus != 'connected':
        return
    self.comm.disconnect(self.selPort, echo=0)    # close the dead port
    self.portStatus = 'disconnected'
    self.btn2.configure(text='Connect')
    stsBarComm.configure(text='Connection to ... lost: the board was switched off or unplugged')
    term.displayText('*** Connection to ... lost ... Switch it on, press RESET and click Connect. ***')
    if self.scriptRunning:
        scriptStop[0] = True                      # a script cannot go on without the board

After this the window is in the same state as in scenario C. Switch the board on, press RESET and click Connect; with Auto connect on it is not repeated automatically.

Cases the two checks cannot see: the board loses power but the USB-serial chip keeps the port alive (that is section 5, not a lost connection), and the board hangs without answering. In the second case the next command times out after two seconds and the Retry / Cancel dialog appears.

7. Known limits

  • Cancel in the timeout dialog ends the program (sys.exit() in boardcom.py). A cleaner exit is on the TODO list.
  • The device is read at connect and from the board's own banner; it is not polled.
  • Only ports whose manufacturer is FTDI are offered. A board with a different USB-serial chip would not be found.
  • A script blocks the window while it runs; a long erase inside a script keeps the Terminal unusable until it finishes.
  • The Classic edition has the same logic with tkinter widgets; its status bar and menus differ only in how they are drawn.
